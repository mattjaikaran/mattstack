# Control Plane & Pluggable Integrations — Design

Date: 2026-08-12
Status: Draft (for review)
Scope: settings-driven strictness, branch protection, pluggable board/notify backends, task SSOT, anti-slop gates, secret hardening, harness-agnostic rules

## Problem

`mattstack-cli` scaffolds and audits code, but enforcement is *convention-by-prompt*, not *config-by-default*. There is no settings-driven strictness toggle, no branch protection, no task/board integration, and no deploy notification. Meanwhile the user's own infrastructure — **Axis** (`~/dev/project-mgmt`, `axis.materialendeavors.com`) and **Hermes** (`~/dev/homelab`, Telegram-driven, Mac mini) — already provides the kanban board, PR-linking, deploy webhooks, and Telegram channel. Mattstack doesn't talk to any of it.

The goal is a **deterministic control plane**: one config file that toggles strictness and protection, and a thin pluggable adapter layer so the *same* commands work against Axis, Hermes' kanban, Linear, Jira, or a generic webhook — regardless of which agent/harness (Claude Code, Orca, Herdr, Hermes, tmux) invokes them.

## Goals

1. **One config file** (`mattstack.yml`) as the single source of strictness truth.
2. **Settings-driven branch protection** — flip `protect_main: true` when a repo goes public/shared.
3. **Pluggable board backend** — `mattstack board` works against Axis, Hermes, Linear, Jira, or a generic sink via one interface.
4. **Pluggable notify backend** — deploy-complete → Hermes (Telegram) / Telegram bot / generic webhook.
5. **Task SSOT** — `tasks/todo.md` + `tasks/completed.md`, synced to the board.
6. **Anti-slop gates** — dependency approval + scope enforcement, deterministic.
7. **Secret hardening** — remove committed/hardcoded secrets; add deeper scanning.
8. **Harness-agnostic rules** — regenerate per-harness adapters from one canonical rule set.

## Non-goals

- Do **not** build a swarm orchestrator (Orca/Herdr/Hermes own that).
- Do **not** rebuild a kanban (Axis is the board; Linear/Jira are one-way adapters).
- Do **not** build a Telegram bot (Hermes is the Telegram channel).
- Do **not** conflict with the in-flight `boilerplate-consolidation` plan (separate v0.7.0 release).
- Do **not** modify boilerplate repos' *standalone* behavior; boilerplate changes are additive gates only.

## Design

### 1. `mattstack.yml` — the config schema

Generated by `mattstack init`, read by every command. Committed to the repo root.

```yaml
version: 1
strict: true              # fail on warnings (ruff/eslint --exit-non-zero-on-fix)
protect_main: true        # branch protection toggle (the "can't push to main" switch)
required_reviews: 1
coverage_floor: 80        # modified-file coverage ratchet (%)
file_length: 400

deps:
  mode: approval          # approval | allow | deny
  manifest: DEPENDENCIES.md

scope:
  enforce: true           # edits restricted to declared plan scope

board:
  backend: axis           # axis | hermes | linear | jira | none
  url: https://axis.materialendeavors.com/api/v1
  api_key_env: AXIS_API_KEY
  project_slug: default

notify:
  backend: hermes         # hermes | telegram | webhook | none
  webhook_url_env: DEPLOY_WEBHOOK_URL
  chat_id_env: TELEGRAM_CHAT_ID
```

Config is loaded by a new `mattstack/config_file.py` (`MattstackConfig` dataclass + `load_config()`). Every existing command that emits warnings/flags consults `strict`.

### 2. Pluggable board backend

A `BoardBackend` protocol (ABC) in `src/mattstack/boards/base.py`:

```python
class BoardBackend(Protocol):
    def create_task(self, title: str, project: str | None = None, **fields) -> dict: ...
    def list_tasks(self, **filters) -> list[dict]: ...
    def update_task(self, task_id: str, **updates) -> dict: ...
    def transition_task(self, task_id: str, target_status: str, comment: str = "") -> dict: ...
    def claim_task(self, task_id: str, agent_name: str) -> dict: ...
    def get_next_task(self, agent_name: str, project: str | None = None) -> dict: ...
    def link_pr(self, task_id: str, pr_url: str, pr_number: int | None = None) -> dict: ...
```

Adapters (each ~100-200 lines, one file):

| Backend | File | Transport | Notes |
|---|---|---|---|
| `AxisBackend` | `boards/axis.py` | HTTP `httpx` → `/api/v1` | Wraps the **same endpoints** Axis's MCP server already wraps |
| `HermesBackend` | `boards/hermes.py` | file/DB | Hermes' own kanban (see Open Question 1) |
| `LinearBackend` | `boards/linear.py` | GraphQL, `LINEAR_API_KEY` | one-way export |
| `JiraBackend` | `boards/jira.py` | REST v3, `JIRA_API_TOKEN` | one-way export |
| `NullBackend` | `boards/none.py` | no-op | `board.backend: none` |

**Axis endpoint map** (from `project-mgmt/mcp/axis-mcp-server.py`, already proven):

| Method | Endpoint |
|---|---|
| `create_task` | `POST /tasks/batch` |
| `list_tasks` | `POST /tasks/search` |
| `update_task` | `PATCH /tasks/bulk-update` |
| `transition_task` | `POST /tasks/{id}/transition` |
| `claim_task` | `POST /tasks/{id}/claim` |
| `get_next_task` | `POST /tasks/next` |
| `link_pr` | `POST /tasks/{id}/link-pr` |

Axis already auto-transitions a task on PR link (`link_pr_to_task`), and has `github_webhook_controller.py` — so the **PR → kanban loop is already built**. Mattstack's job is to call `link_pr` when a PR is created, and to encode the task id in the branch name (Axis's `test_branch_naming.py` already enforces a branch convention).

### 3. Task SSOT

- Canonical files at **project root**: `tasks/todo.md` + `tasks/completed.md` (generated by `mattstack init`).
- `mattstack todo move <item>` moves a checked item `todo.md → completed.md` with date + commit SHA.
- `mattstack board sync` pushes `todo.md` into the configured board (Axis: `POST /tasks/batch`; Linear/Jira: create issues).
- Hermes already treats `~/dev/project-mgmt/tasks/todo.md` as SSOT via `populate-tasks.py`. For *other* projects, mattstack's `board sync` is the sync path.

### 4. Pluggable notify

`src/mattstack/notify.py` with backends `hermes` | `telegram` | `webhook` | `none`, all POSTing a JSON envelope:

```json
{"event": "deploy_complete", "app": "<name>", "commit": "<sha>",
 "env": "production", "frontend_url": "...", "backend_url": "..."}
```

- `hermes` → Axis `deploy_webhook` endpoint (already exists) → Hermes relays to Telegram.
- `telegram` → direct `api.telegram.org/bot<TOKEN>/sendMessage`.
- `webhook` → generic POST to `DEPLOY_WEBHOOK_URL`.
- Wired into `django-ninja-boilerplate/scripts/deploy.sh` as a `notify_deploy` function at the end of the provider `case`, and into the CI deploy job.

### 5. Branch protection (`mattstack protect`)

When `protect_main: true`:

1. Enable `no-commit-to-branch` (main/master) in `.pre-commit-config.yaml` (currently commented out at `django-ninja-boilerplate/.pre-commit-config.yaml:35-36`).
2. Write `CODEOWNERS`.
3. Apply a GitHub branch-protection **ruleset** via `gh api repos/{owner}/{repo}/rulesets`: required PR, ≥`required_reviews` reviews, required status checks (`gauntlet`, `test`), linear history.

Rulesets are API-only (not a committable file), so this must be a CLI action, not a template.

### 6. Anti-slop gates

- **Dependency gate** (`check_dependencies.py` backend + `check_dependencies.ts` frontend): fail if `pyproject.toml`/`package.json` changed but no entry added to `DEPENDENCIES.md`. Registered as a gauntlet gate.
- **Scope enforcement**: `mattstack verify --scope` diffs changed files against the plan's declared scope and fails on out-of-scope touches. This makes "Inspect → Apply → Review" deterministic — an agent physically cannot "clean up" an unrelated service and pass.

### 7. Secret hardening

- Remove hardcoded PostgreSQL password + bare IP in `homelab/scripts/populate-tasks.py:14-20` and `homelab/scripts/recalibrate-axis.py:14-20` → env vars / `.env`.
- Scrub `project-mgmt/cookies.txt` and committed `.env` / `.env.development` files → `.env.example` + gitignore.
- Add `gitleaks` to `.pre-commit-config.yaml` (django boilerplate already has `detect-private-key`; gitleaks adds regex-depth coverage).

### 8. Harness-agnostic rules

- Canonical rule set = `.omp/` + `.context/` files.
- `mattstack rules sync` regenerates the per-harness adapters (`.claude/`, `.cursor/`, `.windsurf/`, `.kiro/`, `.continue/`, `.agents/`) from the canonical source, replacing the currently hand-edited, stale copies in the rsbuild boilerplates.

## Phase ordering

| Phase | Deliverable | Repo | Depends on |
|---|---|---|---|
| 0 | Secret hardening | homelab, project-mgmt, boilerplates | — |
| 1 | `mattstack.yml` + config loader | mattstack-cli | — |
| 2 | `mattstack protect` | mattstack-cli | 1 |
| 3 | `mattstack board` (Axis first, then Linear/Jira/Hermes) | mattstack-cli | 1 |
| 4 | `mattstack todo` + SSOT + `board sync` | mattstack-cli | 3 |
| 5 | `notify` + deploy.sh wiring | mattstack-cli, django boilerplate | 1 |
| 6 | dependency + scope gates | boilerplates, mattstack-cli | 1 |
| 7 | React convention parity (RHF+zod, extracted hooks) | react boilerplates | — |
| 8 | `rules sync` | mattstack-cli, boilerplates | 1 |

Phases 0, 7 are independent and can run in parallel with 1–6.

## Open questions (need your input before Phase 3/5)

1. **What is "Hermes' kanban"?** Hermes (`~/dev/homelab`) has a `tasks/` dir and `archive/todo.md`, and its `populate-tasks.py` writes to the **Axis** DB. Is Hermes' "own kanban" (a) Axis itself, (b) a separate board in homelab, or (c) just its `tasks/todo.md`? This determines whether `HermesBackend` is a real adapter or a file-based no-op.
2. **Linear/Jira: export-only or two-way sync?** Export-only is cheap and safe; two-way sync needs webhook ingestion and conflict handling. Recommend export-only first.
3. **Deploy notification channel**: Hermes→Telegram (recommended, since Hermes already is your Telegram), or direct Telegram bot?
